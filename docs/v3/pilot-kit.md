# KidyCode four-learner pilot kit — preparation only

Status: **DRAFT / NOT APPROVED FOR REAL CHILD TESTING**. Do not recruit, start sessions, create test accounts, or process child data while security issue #9 remains unresolved.

## Participants and privacy
- Intended participants: three children (different approved learner pathways if practical) and one adult. Do not ask for surnames, school names, home addresses, contact numbers, photographs, recordings, or source code containing identifiable data.
- Obtain **explicit informed consent from each child's parent/guardian**, and the child's assent, with a clear right to stop without consequences.
- Use pseudonymous `Tester A`–`Tester D` codes, keep consent records outside the public repository; do not put names or personal information in GitHub issues.
- No surprise screen/audio/video recording; optional recording requires a separate, explicit permission and a deletion policy. Prefer observation notes without recording.
- Explain no grades, no penalty for mistakes, and no promise of certification or academic endorsement.

## Parent/guardian consent request (template)
We are testing KidyCode, an early coding-learning website. We would like your child to try age-appropriate HTML, CSS and JavaScript lessons with a supervising adult. The goal is to see which instructions are clear or confusing; this is not an exam. Participation is voluntary and can stop at any time. We plan to record anonymous observations (tasks attempted, where the learner asks for help, whether they can solve a fresh problem), not their identity, photos or screen recording. Please ask us about the test environment, storage/deletion period and supervision before deciding. No testing will begin until the website passes its privacy and security checks. You may withdraw permission.

## Session guide (draft, 20–40 minutes per learner, flexible)
1. Set expectations: no pressure, learner controls pace, helper does not reveal answers.
2. Onboarding: can learner find the next lesson and understand the objective without assistance?
3. HTML: headings/links — predict outcome; write code; modify a fresh unrelated example.
4. CSS: Flexbox or Grid — decide which element needs the rule, predict arrangement; fix a layout.
5. JavaScript: variables/functions/arrays/loops selected for prior knowledge and age — explain a short snippet, change it, identify an intentionally wrong line.
6. Independence: fresh task with no copied worked solution, explain what changed and why.
7. Debrief: ask which step felt confusing, boring, motivating and what they would change.

## Observation sheet (one per participant, anonymized)
- Test code: Tester A/B/C/D; age **band** only.
- Environment: device class (mobile/tablet/desktop), browser family, accessibility needs expressed voluntarily and without sensitive diagnosis.
- Lesson + course; started/completed; code ran as expected (yes/no).
- Number of optional hints; number of failed attempts; exact error category (not copied private text).
- Need assistance? (none / prompt repeated / conceptual explanation / hands-on).
- Fresh independent task solved? yes / partial / no.
- Could explain why? observed paraphrase / unclear / no.
- Friction notes, next fix, severity, pseudonymous issue reference.
- Delete raw notes on an agreed schedule; never put private records in the repo.

## Acceptance criteria
- Parent/guardian consent and child assent obtained beforehand; secure, invite-only non-production environment checked.
- No unauthorised cross-learner, guardian, cohort or role access.
- Participants can complete a core concept and apply it to a different scenario.
- No serious blockers or distress; assistance patterns are investigated rather than hidden.
- Results summarized without personal data and changes retested.

## Blockers
Security PR #12 identity trust/hosting support; independent review, device/browser verification, user launch approval, guardian consent. **Pilot is not conducted.**
